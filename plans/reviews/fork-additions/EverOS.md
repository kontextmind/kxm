# EverOS → KXM: bounded source audit

## Classification and conclusion

**Category:** persistent agent memory and derived search indexes. **Applicability:** high for M5 memory design; medium for optional integration; low for native streaming/steering. **Disposition:** adapt indexing and retrieval patterns first; evaluate an optional Python component after measuring a concrete retrieval benefit. Keep KXM’s TypeScript control plane, native harness authentication, and independent approval gates.

Reviewed `kontextmind/EverOS` at `5076683ab88d714390573d8f88ff3c470e51129a` against KXM at `5ff9f642e82d7a1e52aeab9245282d89560bb535`. EverOS identifies its upstream as EverMind-AI/EverOS and publishes Python package `everos` 1.3.1. This was static inspection only: no installation, execution, provider requests, or source changes. The unified milestones and runtime-language research informed placement; this report does not replace their implementation tracker. [EverOS manifest](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/pyproject.toml#L1)

## What the code actually provides

EverOS partitions Markdown storage by app/project and user/agent, with SQLite operational state and derived LanceDB indexes. Its scanner reconciles missing, changed, and deleted files; the worker processes queued changes, bounds retries, and handles a file disappearing between enqueue and processing. Search compiles an immutable scope predicate around caller filters. These are implemented mechanisms, beyond README aspirations. [Storage paths](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/core/persistence/memory_root.py#L153), [reconciler](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/memory/cascade/reconciler.py#L64), [worker](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/memory/cascade/worker.py#L757), [scope compiler](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/memory/search/filters.py#L46)

KXM already has authored/candidate Markdown memory, provenance and lifecycle validation, bounded context arbitration, and governed skill promotion. Its recall endpoint currently filters summary/state-key substrings and sorts by ID; its optional provider registry is defined but not wired into this path. Its wiki is explicitly a compiled view, so adopting EverOS must not turn editable wiki output into KXM authority. [Memory implementation](https://github.com/kontextmind/kxm/blob/5ff9f642e82d7a1e52aeab9245282d89560bb535/plugins/kxm/src/memory.ts#L192), [actual recall](https://github.com/kontextmind/kxm/blob/5ff9f642e82d7a1e52aeab9245282d89560bb535/plugins/kxm/src/hub.ts#L1598), [provider seam](https://github.com/kontextmind/kxm/blob/5ff9f642e82d7a1e52aeab9245282d89560bb535/plugins/kxm/src/context/providers.ts#L16), [wiki contract](https://github.com/kontextmind/kxm/blob/5ff9f642e82d7a1e52aeab9245282d89560bb535/plugins/kxm/src/wiki.ts#L7)

## Four concrete adaptations

### 1. Scoped ranked recall behind KXM’s existing surface — M5, effort M

Extend `plugins/kxm/src/context/providers.ts` with query, deadline, and explicit scope inputs; integrate through `hub.ts`’s authenticated context routes and `arbiter.ts`. Add `context/index-provider.ts` as an internal backend. Borrow EverOS’s reserved scope fields and backend-neutral predicate construction; resolve scope from KXM’s authenticated caller rather than model-provided owner IDs. Revalidate returned project, provenance, lifecycle, and authority in KXM. Begin with keyword ranking over approved sources; vectors/reranking require separate measured value and explicit capability setup. EverOS’s service builds optional search dependencies lazily, while its manager selects distinct keyword/vector/hybrid paths. [Search wiring](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/service/search.py#L97), [KXM arbitration call](https://github.com/kontextmind/kxm/blob/5ff9f642e82d7a1e52aeab9245282d89560bb535/plugins/kxm/src/hub.ts#L1573)

**Acceptance:** identical scoped requests through CLI/MCP/native adapters return the same bounded candidates; nested OR filters and malicious provider results cannot cross projects; backend failure shrinks context; a held-out query set improves retrieval over current substring matching without increased authority.

### 2. Recoverable derived-index lifecycle — M5, effort M–L

Add `context/index-reconciler.ts` and `context/index-store.ts`; connect source revisions from `memory.ts` and `runtime-service.ts`. Adapt EverOS’s scan-versus-state reconciliation, deletion recovery, retry classification, and cheap watcher enqueue. Preserve KXM’s canonical records and run-pinned memory revision; use content hashes alongside file observations rather than copying EverOS’s mtime-only unchanged decision. A pending index must report lag, not silently imply freshness. KXM already hashes authored memory and promoted skills at run creation. [EverOS unchanged/deletion decisions](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/memory/cascade/reconciler.py#L94), [KXM revision hashing](https://github.com/kontextmind/kxm/blob/5ff9f642e82d7a1e52aeab9245282d89560bb535/plugins/kxm/src/runtime-service.ts#L115)

**Acceptance:** restart mid-index, missed deletion, atomic replacement, unchanged timestamp with changed bytes, and unavailable embedding service all converge without resurrecting superseded evidence. Rebuild yields the same source hashes and scope. EverOS already contains missed-deletion/retry reconciler tests worth adapting as scenarios. [Existing tests](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/tests/unit/test_memory/test_cascade/test_reconciler.py#L107)

### 3. Learning suggestions enter candidate review — M6, effort M

Add `context/learning-candidates.ts`, using `memory.ts:createMemoryNote` and `skills.ts:SkillLifecycle.create`. EverOS reconstructs cases, retrieves supporting examples, runs an extractor, then writes emitted skills and removes renamed predecessors. Reuse the supporting-case/provenance idea; do not import its direct write-back lifecycle. KXM must retain evidence receipts, immutable content, protected evaluations, and a promoter distinct from the author. [EverOS extraction/write-back](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/memory/strategies/extract_agent_skill.py#L182), [KXM promotion](https://github.com/kontextmind/kxm/blob/5ff9f642e82d7a1e52aeab9245282d89560bb535/plugins/kxm/src/skills.ts#L387)

**Acceptance:** a generated “skill” requesting new permissions remains evidence/candidate content; self-promotion fails; stale or modified source receipts invalidate evaluation; generated renames cannot delete promoted skills. Any extraction model call follows KXM’s admitted native route, without copying native credentials into EverOS configuration or silently choosing another provider.

### 4. Explicit optional-component readiness — M1/M9, effort M; Python experiment L

Extend `cli.ts`, `cli/system.ts`, `hub.ts`, and `cli/hub.ts`, with proposed `components/memory-runtime.ts` for component identity/health. KXM already distinguishes `/health` from storage `/ready`; EverOS adds capability flags, index backlog, and operational degradation. Expose those separately so one unhealthy optional index does not misrepresent core availability. [KXM probes](https://github.com/kontextmind/kxm/blob/5ff9f642e82d7a1e52aeab9245282d89560bb535/plugins/kxm/src/hub.ts#L1111), [EverOS readiness](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/entrypoints/api/routes/health.py#L77)

**Acceptance:** one npm-installed KXM exposes explicit setup/status/removal; absent Python leaves baseline memory usable; setup failure preserves the previous component; normal requests perform no package synchronization or download. If admitted, pin Python, component version and uv lock outside the user project, and test packed-consumer behavior on supported platforms using the existing `test/core/package-install.test.ts` suite.

## Runtime, packaging and limits

EverOS requires Python 3.12+, has a uv lock and CLI entrypoint, and depends on LanceDB plus pinned separately published `everalgo` packages. No first-party `.rs` or `Cargo.toml` appeared in the inspected inventory. Native dependencies do not establish that rewriting KXM in Rust helps. KXM remains a Node/TypeScript package; compare startup, memory, retrieval quality, latency and platform support before adding another runtime. EverOS’s dependency comments document a clean-install mismatch despite local lockfile success, making installed-artifact tests especially relevant. [Dependency pins](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/pyproject.toml#L79), [KXM package](https://github.com/kontextmind/kxm/blob/5ff9f642e82d7a1e52aeab9245282d89560bb535/package.json#L23)

A significant integration caveat: the search service tolerates no LLM, but default FastAPI startup installs `LLMLifespanProvider`, which requires LLM configuration. An offline keyword-only component therefore needs a deliberate narrowed composition; starting the stock server is not proof of credential-free operation. Generated SKILL.md records likewise are not already compatible KXM promoted skills. [Actual startup requirement](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/entrypoints/api/lifespans/llm.py#L22), [default composition](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/entrypoints/api/app.py#L85)

**M0–M9 placement:** M0 supplies redaction/truthful readiness; M1 component admission; M2/M3 retain separate streaming/steering work; M4 no direct contribution; M5 indexing/recall; M6 candidate learning; M7 can display index state; M8 only explicit capability setup under KXM auth ownership; M9 validates packaged cross-harness behavior. EverOS’s inspected search HTTP route returns one completed response, not a native session-control protocol. KXM’s one-shot runner still collects stdout until settlement: neither uv nor this memory engine resolves that. [EverOS endpoint](https://github.com/kontextmind/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/entrypoints/api/routes/search.py#L19), [KXM buffering](https://github.com/kontextmind/kxm/blob/5ff9f642e82d7a1e52aeab9245282d89560bb535/plugins/kxm/src/oneshot-process.ts#L55)

# OpenViking: shared memory and future KXM Studio

## Decision and review boundary

**Category:** context database, extraction/indexing runtime, and browser operator application. **Relevance:** high as an architectural reference for M5/M7; medium as an optional backend; low as a replacement for KXM orchestration. **Disposition:** independently adapt bounded retrieval, provenance views, and durable work contracts; defer bundling the server or copying its Studio until licensing, platform packaging, and workload value are resolved.

This separate review inspected `kontextmind/OpenViking` at **192b813e7e3106680a5534e2d4c9bcf6d2390abd**, forked from `volcengine/OpenViking`, against current KXM **02aaed31fd6160a78378c677ab27d4119f039621**. Selected implementation files were fetched at the pinned revision using the supplied complete path inventory. No installation, repository execution, provider access, or KXM/plan modification occurred. KXM's AGENTS and sole implementation tracker were read as context; this report proposes work without creating another tracker. Existing runtime hardening was not assumed to repair unrelated memory or Studio paths.

## Implemented behavior and current overlap

### Retrieval is more substantial than a vector-search wrapper

OpenViking's hierarchy traversal uses a priority queue, batched child searches, inherited directory/query scores, URI deduplication, and convergence checks. These are approximate retrieval heuristics, not exhaustive search or measured accuracy guarantees. Its scope builder combines account visibility, path targets, caller filters, and requested levels; ordinary ACL checks and administrative/root behavior are explicitly different. KXM should preserve its own caller-to-project binding instead of mapping a KXM worker to OpenViking root. [Hierarchy implementation](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/openviking/retrieve/hierarchical_retriever.py#L478-L588), [scope construction](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/openviking/storage/viking_vector_index_backend.py#L2191-L2259)

The context assembler centralizes retrieval, detail planning, rendering, optional rewriting, and session deduplication. It reads bodies only when a planned tier needs them. A failed dedup ledger write is explicitly best-effort. The detail choices are URI, abstract, overview, and full content: an absent resource/skill abstract normally falls back to a URI rather than silently reading raw content. These presentation tiers are separate from index levels L0/L1/L2. [Assembly pipeline](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/openviking/retrieve/context_assembler/pipeline.py#L75-L146), [detail boundaries](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/openviking/retrieve/context_assembler/tiers.py#L170-L230)

Sharing is not synonymous with strict isolation: gathering defaults to `peer_scope="all"`, constructs a context without actor-peer restriction, and penalizes other-peer scores. That can be useful within one user's admitted shared space, but score penalties are not permissions. KXM's project/role/run boundaries need an explicit mapping. [Peer gathering](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/openviking/retrieve/context_assembler/gather.py#L204-L255)

KXM already has role-aware, deterministic context arbitration, contradiction priority, lifecycle filtering, token estimates, and shared context APIs. Its recall endpoint still performs substring matching and ID sorting. Its provider seam supplies project/kinds/limit but no query and is not used by the inspected recall path. Thus the useful addition is ranked, tiered retrieval behind existing surfaces, not another independently installed memory plugin for each harness. [Current recall](https://github.com/kontextmind/kxm/blob/02aaed31fd6160a78378c677ab27d4119f039621/plugins/kxm/src/hub.ts#L1599-L1617), [current arbitration](https://github.com/kontextmind/kxm/blob/02aaed31fd6160a78378c677ab27d4119f039621/plugins/kxm/src/arbiter.ts#L183-L213), [provider contract](https://github.com/kontextmind/kxm/blob/02aaed31fd6160a78378c677ab27d4119f039621/plugins/kxm/src/context/providers.ts#L16-L33)

### Writes have provenance, but do not implement KXM promotion

OpenViking's updater reads current content, applies schema merges, stamps extraction/trace identifiers, and writes memory files. It suppresses same-batch delete/upsert conflicts and then updates vectors, links, and overviews. This is a mutable learned-memory workflow, not proof of independent review. KXM must retain its origin-authority ceiling and protected skill promotion: external/derived content remains evidence; the author cannot promote their own skill, and evaluations/evidence are required. [Updater and trace metadata](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/openviking/session/memory/memory_updater.py#L1084-L1126), [KXM authority](https://github.com/kontextmind/kxm/blob/02aaed31fd6160a78378c677ab27d4119f039621/plugins/kxm/src/context.ts#L26-L40), [KXM promotion](https://github.com/kontextmind/kxm/blob/02aaed31fd6160a78378c677ab27d4119f039621/plugins/kxm/src/skills.ts#L387-L418)

Session commit persists archive information/messages, enqueues extraction, publishes retained state, and records phase readiness. Resume checks terminal markers and can requeue work that cannot yet run. The inspected deletion implementation checks access, takes path locks, deletes vector rows, then removes files; missing files trigger orphan-index cleanup. This is useful recovery-oriented code, but the ordering alone does not establish an atomic cross-store transaction or exactly-once extraction. [Archive/queue ordering](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/openviking/session/session.py#L2130-L2214), [resume markers](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/openviking/session/session.py#L2302-L2367), [deletion ordering](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/openviking/storage/viking_fs/_ops.py#L224-L258)

### Studio is a real application, with transferable boundaries

The React/Vite Studio separates query hooks, API types, and components. Retrieval controls send scope, time, tags, levels, and provenance options. The session memory-impact view computes add/update/delete counts and filters changes by memory type; its underlying diff model carries archive identity and before/after text. That is a good product model for explaining what an agent learned. It must be extended with KXM's proposed/approved/rejected states, rather than treating every extraction as accepted knowledge. [Retrieval query seam](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/web-studio/src/routes/retrieval/-hooks/use-retrieval-query.ts#L11-L71), [memory-impact view](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/web-studio/src/routes/sessions/-components/memory-impact.tsx#L52-L107)

KXM already serves Studio layout data and mutation callbacks. At this exact current revision, absent `onMutation` still returns `ok:true` and `executedAt`; that remains a prerequisite repair, not a defect inferred from the older audit. KXM also already has authenticated operations snapshots/SSE, so a new UI should consume that service rather than invent another task database. [Current mutation fallback](https://github.com/kontextmind/kxm/blob/02aaed31fd6160a78378c677ab27d4119f039621/plugins/kxm/src/studio-layout.ts#L410-L430), [existing operator stream](https://github.com/kontextmind/kxm/blob/02aaed31fd6160a78378c677ab27d4119f039621/plugins/kxm/src/hub.ts#L1395-L1427)

## Language, setup, licensing, and remaining limits

This is a mixed runtime: Python 3.10+ service/extraction, C++ vector engine, Rust CLI/RAGFS, and TypeScript Studio. `setup.py` builds the CLI, Rust binding, and C++ extensions; the Rust Python binding requires Rust 1.91.1 and uses PyO3's Python 3.10 stable ABI. Published wheels may avoid compilers, but this review did not verify wheel availability or installed behavior on any platform. uv could manage a pinned Python component; it would neither remove native dependency support nor accelerate Python orchestration by itself. [Native build entry](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/setup.py#L107-L119), [Rust binding manifest](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/crates/ragfs-python/Cargo.toml#L1-L23)

The Python distribution declares **AGPL-3.0**, matching inspected server SPDX headers and root LICENSE. The separate npm CLI manifest declares **Apache-2.0**, platform optional packages, and a postinstall hook. That declaration does not establish that the server or Studio can be copied into MIT KXM under Apache terms. Resolve component-specific licensing before redistribution or source reuse; independent implementation of the architectural ideas is the preferred next step. KXM already exposes core/runtime/client/extension/MCP bundles, so one installation does not require transplanting OpenViking's CLI or per-harness credential configuration. [Python license/runtime declaration](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/pyproject.toml#L1-L32), [npm declaration](https://github.com/kontextmind/OpenViking/blob/192b813e7e3106680a5534e2d4c9bcf6d2390abd/npm/cli/package.json#L1-L24), [KXM public bundles](https://github.com/kontextmind/kxm/blob/02aaed31fd6160a78378c677ab27d4119f039621/package.json#L54-L82)

**Milestone coverage:** M0 truthful results/redaction precedes exposing bodies; M1 explicit capabilities/setup; M2 shared stream delivery; M3 native steering remains independent; M4 gains only document/source preview adjacency; M5 is the main retrieval/durability work; M6 controls learned candidates; M7 adds the explorer/review UI; M8 retains KXM-owned provider authentication and explicit model capability setup; M9 validates the assembled package across admitted harnesses. Never copy native credentials to satisfy an extraction backend or silently switch providers.

Source tests for context assembly and session resume were inspected, including fake storage and mocked extraction; they are useful test scenarios, not demonstrated production recovery. No performance, isolation, cross-store atomicity, model quality, or live cross-harness claim was runtime-verified. **Recommended next slice:** an independently implemented tiered context API with an evidence-first Studio read view, retaining KXM as the sole authority and task service.

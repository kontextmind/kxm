# Yao → KXM: coordinator inbox and task workspaces

**Category:** full agent application platform: Go host, conversational/task agents, robot orchestration, workspace management, OpenAPI, and messaging. **Relevance:** high for future primary/coordinator interaction and Studio; medium for runtime patterns; low for wholesale adoption. **Disposition:** implement selected ideas in KXM's existing TypeScript services. **Priority:** reliable M0/M2/M3 contracts first; coordinator inbox and memory visibility under M5/M7/M8.

## Version, source, and adoption boundary

This separate review pins `kontextmind/yao` to **5774ce8de5a4d832a1808d942f87c60de86c78e7** and KXM to **02aaed31fd6160a78378c677ab27d4119f039621**. Exact downloaded paths/hashes are in this batch's `yao-metadata.json`. This is static source analysis: no runtime, provider call, installation, interoperability test, or benchmark was performed. Current KXM AGENTS and the unified harness strategy inform scope, not Yao's repository instructions.

**Licensing materially limits code reuse.** The pinned LICENSE calls itself modified Apache 2.0 and adds branding/certificate-preservation provisions plus commercial-license conditions for organizations with at least 50 employees or revenue above $1 million. Do not label this ordinary Apache-2.0 or assume it can be silently rebranded into KXM. Prefer independent implementation of architectural patterns; evaluate specific redistribution terms before incorporating code. [Pinned license](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/LICENSE#L1-L30).

The public fork provides substantial server implementation, but not the current complete client application source. Its `ui/index.html` contains only `## UI ROOT`; release rules separately clone/build CUI, and some development builds expect a sibling `cui-v1.0` checkout. Therefore this review supports API and state-model lessons, not claims that the advertised desktop/mobile UI can be lifted from this tree. Builds use Go 1.25 and CGO; Windows recipes require LLVM, while client assets require a separate pnpm build. A Go executable does not make this a dependency-free replacement for KXM. [Client assembly](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/Makefile#L758-L814), [Go module](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/go.mod#L1-L55).

## What actually runs

Yao separates three mechanisms. The assistant executes model/tool turns. A task daemon invokes that assistant independently of HTTP connections, with a team quota and persisted task status. The robot executor adds ordered phases/tasks, previous-result context, human-input suspension, and delivery evaluation. These are genuine implementations, not just board mock data. Conversely, success in the robot's run phase means the call returned successfully; overall quality is delegated to a later agent, with continue-on-failure enabled by default. That cannot substitute for KXM's deterministic artifact/check acceptance. [Robot execution semantics](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/agent/robot/executor/standard/run.go#L14-L39).

There is a misleadingly named `schedule_stub.go`, but normal server startup replaces it with `NewScheduleEngine()` and starts the engine. Do not report scheduling as absent. Its minute ticker and separate robot scheduler nevertheless should not become additional owners of KXM workflow execution. [Production scheduler wiring](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/cmd/start.go#L175-L188).

Tool handling offers useful tracing/cancellation seams, but the MCP path groups calls by server and can retry the whole server batch sequentially after a retryable parallel error. A partly successful batch must not be retried blindly in KXM; use per-effect identities and evidence of which calls actually ran. [Tool batch retry](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/agent/assistant/mcp.go#L417-L478).

## Five useful adaptations

### 1. Coordinator inbox derived from authoritative task events

**M0/M7/M8; medium.** Yao maps waiting/completed/failed states to input/completed/failed notices, retaining chat, assistant, board, creator, and team references. This is a good model for the user's primary/coordinator inbox: prioritize decisions and failures, show the affected work, and make the next action concrete. However, mail insertion, unread updates, and event publication are separate operations. More seriously, result enrichment accepts an LLM-provided run status and converts missing/invalid status to `completed` unless execution errors override it. KXM should generate notice state from verified Runtime events and use model text only for the summary. [Inbox generation](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/agent/inbox/trigger.go#L13-L85), [enrichment status assignment](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/agent/task/enrich_result.go#L148-L171).

**Landing:** proposed `plugins/kxm/src/operator-inbox.ts`, `runtime-store.ts`, `hub.ts`, and `studio-layout.ts`. Persist an inbox projection/outbox transactionally with the source event; reference project/run/attempt/evidence and track unread independently of execution state.

SMS can be an explicit optional delivery adapter. Yao has a real Twilio send path and an inbound converter, but the converter itself only parses form fields and has no signature verification; that observation does not establish what all outer middleware does. Transport success also is not delivery or human approval. Keep authenticated callbacks, recipient consent/configuration, receipts, and approved costs in KXM's adapter. [SMS send path](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/messenger/providers/twilio/twilio.go#L271-L301), [inbound conversion](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/messenger/providers/twilio/twilio_receive.go#L11-L98).

**Acceptance:** replaying one terminal event creates one notice; a stale enrichment reply cannot overwrite a newer attempt; an invalid summary/status never manufactures completion; failed delivery remains pending/failed; forged or duplicate SMS callbacks cannot resume work; opening/reading a notice never approves an action.

### 2. Background execution with bounded, recoverable observation

**M0/M2/M7; medium–large.** Yao's daemon registry prevents duplicate concurrent runs within one process and queues work under team quota. That is useful separation of command admission from observation, but the registry/queue are not a durable distributed claim. Its so-called ring buffer appends every message under a per-message size threshold without a total bound; full subscriber channels drop messages. `Watch` switches between live replay and database history, but a database error can become an empty `read_complete`, and the live sequence is not a durable cross-restart cursor. [Run admission](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/agent/task/run.go#L27-L96), [buffer and drops](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/agent/task/daemon.go#L101-L130), [history fallback](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/agent/task/watch.go#L23-L98).

**Landing:** `runtime-store.ts`, existing supervisor drive boundary, proposed `studio-events.ts`. KXM already validates project/runtime ownership when appending events and reads ordered pages after a sequence. Reuse that store for live progress; add explicit gaps, rebaseline, byte limits, and observation errors rather than copying the memory buffer. [Existing KXM event boundary](https://github.com/kontextmind/kxm/blob/02aaed31fd6160a78378c677ab27d4119f039621/plugins/kxm/src/runtime-store.ts#L774-L808).

**Acceptance:** reconnect after process restart yields an ordered snapshot plus events; dropped/expired cursors trigger an explicit rebaseline; database failure is distinguishable from empty history; slow clients stay bounded; tab closure never cancels the job; repeated admission after an uncertain HTTP response cannot duplicate an external effect.

### 3. Stable workspace/session bindings and layered cancellation

**M0/M1/M3/M9; medium.** Yao workspace records carry immutable owner/node bindings. The DSH runner initializes a working directory and reuses the chat ID as the native session ID, including across assistant changes. That supports continuity, but KXM needs an explicit binding of project, checkout/worktree, harness, native session, and configuration revision rather than a chat string alone. [Workspace ownership](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/workspace/workspace.go#L42-L74), [DSH identity mapping](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/agent/sandbox/v2/dsh/command.go#L137-L160).

The DSH session uses a useful cancellation ladder: session-cancel RPC, shutdown RPC, POSIX TERM, then force kill. Yet Yao's WebSocket stop/cancel command ignores the Stop error and immediately emits `stream_end`. This is stream termination, not verified task settlement. KXM A1 already preserves escalation after child close and reports unverified descendants; retain those guarantees. [DSH cancellation ladder](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/agent/sandbox/v2/dsh/session.go#L130-L181), [WebSocket stop response](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/openapi/agent/task/ws.go#L121-L141), [current KXM A1](https://github.com/kontextmind/kxm/blob/02aaed31fd6160a78378c677ab27d4119f039621/plugins/kxm/src/oneshot-process.ts#L79-L126).

**Landing:** `harness.ts`, `oneshot-process.ts`, `runtime-store.ts`, and the proposed session adapter. Also enforce resource authorization in every read/stop path: Yao's inspected `Stop` and `Watch` take auth but do not perform the task ownership lookup themselves. OAuth route authentication alone is not evidence that these operations bind the correct task.

**Acceptance:** wrong-project session/read/stop rejects; changed worktree prevents implicit resume; requested cancellation, acknowledged cancellation, process exit, and uncertain effects remain separate; RPC failure escalates within bounds; native-model auth cannot silently become a different paid route; Windows/POSIX cleanup outcomes are reported honestly.

### 4. Durable requests for human input, including coordinator replies

**M0/M3/M7/M8; medium.** Robot suspension records the waiting task, question, task index, and prior results; startup recovery preserves waiting/confirming executions while marking interrupted running/paused/pending work failed. This is better than losing the question with the browser. However, suspension logs persistence failures and proceeds; recovery is not proof that external effects were undone. Use the interaction model with KXM's stronger transactional/effect semantics. [Suspend state](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/agent/robot/executor/standard/executor.go#L738-L774), [restart treatment](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/agent/robot/manager/recovery.go#L17-L67).

**Landing:** existing wait/signal handlers in `hub.ts`, `runtime-store.ts`, and inbox detail UI. A reply must identify the exact run/stage/attempt/question and authenticated actor; informational answers and approvals are different commands. KXM already verifies signed workflow callbacks and rejects reused delivery IDs with different payloads. [Current callback receipts](https://github.com/kontextmind/kxm/blob/02aaed31fd6160a78378c677ab27d4119f039621/plugins/kxm/src/hub.ts#L1124-L1156).

**Acceptance:** crash after asking restores the same unresolved question; persistence failure does not claim a durable wait; duplicate replies have one effect; stale replies cannot authorize changed arguments or another attempt; cancelling a wait invalidates later approvals; interrupted side effects remain uncertain until reconciled.

### 5. Visible memory scope and retention without weakening provenance

**M5/M6/M7; medium.** Yao's memory API separates user, team, chat, and request context namespaces, with explicit default TTLs: persistent user/team, 24-hour chat, 30-minute context. Namespaces are storage prefixes, not semantic evidence or promotion controls; they do not include KXM's project identity. Do not substitute team-wide mutable key/value memory for reviewed project knowledge. [Scopes and TTL implementation](https://github.com/kontextmind/yao/blob/5774ce8de5a4d832a1808d942f87c60de86c78e7/agent/memory/memory.go#L10-L100).

**Landing:** `context.ts`, `memory.ts`, `context/providers.ts`, and Studio memory inspector. Show origin, scope, validity, lineage, and why a record was included; add bounded ephemeral caches where useful. KXM already has agent/project/run/operator scopes, immutable provenance, validity intervals, supersession, and evidence references. Extend presentation/retention policy rather than create a second memory authority. [KXM context contract](https://github.com/kontextmind/kxm/blob/02aaed31fd6160a78378c677ab27d4119f039621/plugins/kxm/src/context.ts#L87-L128).

**Acceptance:** same chat/user labels in two projects cannot collide; expired context is excluded reproducibly; edits mint new provenance; clearing a cache cannot delete approved knowledge; received SMS/mail and generated summaries cannot promote themselves to instruction/policy; all harness surfaces retrieve the same approved records.

## Studio and delivery decision

The five patterns belong behind one KXM installation and shared API. Current Studio's optional token enforcement and success response without a mutation handler must be fixed before exposing coordinator actions; Yao's larger endpoint catalog does not solve that boundary. [Current Studio mutation behavior](https://github.com/kontextmind/kxm/blob/02aaed31fd6160a78378c677ab27d4119f039621/plugins/kxm/src/studio-layout.ts#L345-L430).

M4 keeps KXM's browser service; M6 keeps governed skills; M8 owns explicitly configured message transports; M9 proves packaged behavior across harnesses and platforms. Defer Yao's independent schedulers, complete Go/Tai host, separate CUI packaging, and model-driven acceptance decisions. No source evidence here establishes a performance reason to move KXM orchestration from TypeScript to Go. These are proposed acceptance checks, not executed tests or passed milestone gates.
